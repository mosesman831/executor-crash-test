Executor crash test / Introduction
01 / The purpose

What happens when an agent is interrupted?

We built a small crash-test prototype to help people see what an AI agent did, what went wrong and what evidence remains.

It turns a live experiment into a shared view that a team can inspect together.

The practical questionCan we tell which work actually finished?
02 / Why it matters

An interruption can leave work uncertain.

Imagine an agent preparing a file when its working environment disconnects. A team needs to know whether the file exists and whether it contains the right information.

These tests explore that question with a small, controlled task before drawing conclusions about a larger system.

The benefitFind evidence gaps while there is still time to investigate.
03 / The agent

A model decides; tools do the work.

An agent uses an AI model to work through a task and can call tools to perform actions. In this demonstration, the model is gpt-6-luna, and the task involves running commands and working with a file.

LunaThe model directs the agent during the experiment.
04 / The workspace

The test uses an OpenAI-hosted sandbox.

The OpenAI Agents API creates the agent session and provides the stream of activity. The agent works in a hosted sandbox: a temporary, isolated workspace for running the test.

The harness sends a preset task and collects the available records.

Three rolesAPI: session and events. Model: decisions. Sandbox: workspace.
05 / Step 1 / Choose

Pick the baseline or the interruption.

Choose a preset and select Start live test. The sequence is:

  1. Create a hosted session.
  2. Open the event stream.
  3. Send the preset task.
  4. Run the task and, for F1, attempt the fault.
  5. Retrieve saved evidence.
  6. Show a verdict based on that evidence.

The real API calls use credits. You can end the session on the page.

Your choiceF0 checks an ordinary run. F1 attempts a controlled interruption.
06 / Step 2 / Baseline

F0 checks that ordinary work succeeds.

  1. The agent creates and reads step1.txt, containing exactly alpha with no newline.
  2. The harness checks the completed turn and successful commands.
  3. It downloads the file and checks its SHA-256 fingerprint against the expected value.
Expected SHA-256

8ed3f6ad685b959ead7022518e1af76cd816f8e8ec7ccdda1ed4018e8f2223f8

A matching download verifies the exact expected bytes.

07 / Step 2 / Interruption

F1 attempts a controlled fault.

  1. The agent first creates and reads the same alpha file, then writes a probe before the fault.
  2. It is asked to attempt a signal once, only if its direct parent is identified as codex.
  3. The harness watches for a disconnect and examines the saved trace for the attempted signal and its effects.
ExperimentalA disconnect does not confirm a kill, file survival or recovery.
08 / Step 3 / Observe

Follow the work as it happens.

The live page shows a plain-language activity feed alongside the raw JSON events sent by the API. The status and stage indicators show where the run has reached.

Open Saved trace and items after the turn to inspect the records used for the evidence check.

Two viewsRead the explanation, then compare it with the source events.
09 / Step 4 / Assess

The result follows the evidence.

For F0, a pass needs a completed agent turn, successful command evidence and a matching downloaded file. Missing evidence cannot produce a pass.

F1 is experimental and is reported as inconclusive: even useful trace markers do not independently establish signal completion, executor identity, file survival or recovery.

Evidence has limitsA recorded event tells us what was observed, not everything that happened.
10 / Working with Codex

A shared test can start from Codex.

Codex can use the harness through MCP, a standard way for an assistant to use external tools. It can start a preset hosted test, and this page can follow that same run and inspect saved evidence.

Codex also helped implement the event parser that makes the stream easier to read.

One experimentCodex starts the test; the live page makes its progress visible.
11 / What you can do

Run, inspect and discuss.

  1. Start with F0 to see a normal file check.
  2. Try F1 to observe the experimental interruption.
  3. Compare the activity feed, raw events and saved evidence with the verdict.

Use the results to identify questions for further testing. This prototype is not a guarantee of production resilience.
